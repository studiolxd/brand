# Internacionalización

Los componentes de la librería emiten textos por su cuenta: etiquetas accesibles (`aria-label`,
texto para lectores de pantalla) y, en algunos casos, texto visible en pantalla — un mensaje de
"sin resultados", el sumario de una paginación, la zona de arrastre de un campo de archivos.

Hay **dos formas** de que esos textos lleguen traducidos, y el sistema está migrando de la
primera a la segunda:

1. **Props de texto con default castellano** — la convención histórica, y todavía la de la
   inmensa mayoría de componentes.
2. **El proveedor de textos** (`BrandMessagesProvider`) — el destino: el texto sale del catálogo
   de la aplicación y **no hay default**, así que olvidarlo es un error, no un castellano mudo.
   Hoy lo usan `Pagination` y la **familia de tablas** (`Table`, `DataTable`).

## El proveedor de textos

Se monta **una vez en la raíz de la aplicación**, con el catálogo del idioma vigente:

```tsx
import { BrandMessagesProvider } from '@studiolxd/brand/messages';

<BrandMessagesProvider
  messages={{
    pagination: {
      label: t('pagination.label'),
      pagesGroup: t('pagination.pagesGroup'),
      previous: t('pagination.previous'),
      next: t('pagination.next'),
      goToPage: (page) => t('pagination.goToPage', { page }),
      perPage: t('pagination.perPage'),
      total: (count) => t('pagination.total', { count }),
      allOption: t('pagination.allOption'),
    },
    table: {
      actions: t('table.actions'),
      sortable: t('table.sortable'),
      sortedAscending: t('table.sortedAscending'),
      sortedDescending: t('table.sortedDescending'),
    },
    dataTable: {
      empty: t('dataTable.empty'),
      search: t('common.search.placeholder'),
    },
  }}
>
  {children}
</BrandMessagesProvider>
```

A partir de ahí, un componente migrado se monta **sin una sola prop de texto**:

```tsx
<Pagination total={200} page={3} pageSize={10} showTotal onPageChange={setPage} />
```

### Cómo está hecho

- **El tipo nace en el DS.** `BrandMessages` es el contrato, y el catálogo de la app es quien lo
  satisface — nunca al revés. Si el tipo se generase desde el JSON de una suite, el DS dependería
  de un paquete de producto para declarar su propio contrato.
- **Anidado por componente, no plano.** Un espacio por componente (`pagination`, `table`,
  `dataTable`, y los que vengan), calcando los que el catálogo de la suite ya tiene. Son 310 textos: una lista plana de
  claves sueltas no se puede escribir ni revisar.
- **Todas las claves son obligatorias** dentro de su espacio, como en `RecoveryCodesLabels`. Una
  app que se deje una **no compila**: ese es el punto entero del mecanismo.
- **La interfaz de cada espacio vive junto a su componente** (`PaginationMessages` se exporta
  desde `Pagination`), y `BrandMessages` solo las ensambla.

### El orden: prop → proveedor → error

| Escalón | Cuándo |
| --- | --- |
| **La prop** | Cuando se pasa. Es la anulación puntual, para el uso que de verdad no dice lo mismo que todos los demás |
| **El proveedor** | Cuando la prop falta |
| **Un error** | Cuando faltan las dos, con el nombre del texto que falta |

**No hay cuarto escalón.** Un default castellano viaja dentro del paquete y se alcanza en
ejecución: pinta "Página 3" dentro de una interfaz en francés sin que falle nada, sin que lo vea
ningún test, y se ve bien estando mal. El error se lanza **donde el texto se pinta**, así que un
componente no exige el texto de una pieza que no enseña.

### Y el Storybook, ¿no es un default por la puerta de atrás?

No, y la diferencia es de sitio, no de matiz. El Storybook es **la aplicación que monta los
componentes**, así que monta el proveedor como lo hará cada app: un decorador global
(`.storybook/preview.tsx`) lo envuelve todo con un fixture castellano
(`.storybook/brandMessagesFixture.ts`).

Ese fixture **no puede llegar a un consumidor**: vive fuera de `src/`, no es punto de entrada de
la librería, ningún componente lo importa y `package.json#files` solo publica `dist/`,
`src/tokens/` y el `CHANGELOG`. Las cuatro cosas las vigila un test
(`src/messages/BrandMessages.test.ts`), no un comentario que lo prometa. Un default, en cambio,
viaja dentro del `.js` compilado y se alcanza desde cualquier app que olvide un texto.

## La convención histórica (props con default)

Mientras el componente no esté migrado al proveedor, cada texto que emite por su cuenta es una
**prop opcional con el texto castellano como valor por defecto**. Una aplicación multiidioma que
no las pase **pierde sus traducciones**: un usuario de lector de pantalla en inglés o en alemán
oye "Página 3" o ve "Sin resultados" en medio de una interfaz traducida — el fallo silencioso que
el proveedor viene a cerrar.

Cada texto que el componente emite por su cuenta es una **prop opcional con el texto castellano
como valor por defecto**:

```tsx
// sin props → castellano
<Modal open={open} onOpenChange={setOpen} title="Ajustes" />

// con props → los textos del consumidor
<Modal
  open={open}
  onOpenChange={setOpen}
  title={t('settings.title')}
  closeLabel={t('common.close')}
  fallbackTitle={t('common.dialog')}
/>
```

Reglas de la convención:

- **El default es siempre el texto castellano actual**, así que añadir la prop nunca es un
  breaking change ni cambia el marcado de quien no la pasa.
- **Nombre `<cosa>Label`** para etiquetas accesibles y textos cortos; `<cosa>Message` para
  mensajes; `<cosa>Error` para textos de error; `<cosa>Hint`/`<cosa>Placeholder` para pistas.
- **Función en vez de string** cuando el texto interpola un valor:
  `pageLabel?: (page: number) => string`, no un string con marcador.
- **Listas de opciones se traducen pasando la lista entera**, no con una prop de texto por
  elemento: `pageSizeOptions` en `Pagination`, `legendItems` en `CalendarRoster`.
- **El JSDoc de la prop dice cuál es el default y que es castellano**, para que se vea desde el
  autocompletado del editor.

## Fechas y números

Los componentes de calendario no traducen nombres de mes y día con props de texto: reciben una
prop **`locale`** (default `'es-ES'`) y delegan en `Intl.DateTimeFormat`. Las props de texto de
esos componentes cubren solo lo que `Intl` no da — los `aria-label` de navegación, la leyenda.

```tsx
<Calendar locale="de-DE" previousMonthLabel="Vorheriger Monat" nextMonthLabel="Nächster Monat" />
```

Lo mismo vale para el **orden de la fecha escrita** en `DatePicker`: `25/09/2026` en `es`,
`09/25/2026` en `en-US` y `25.09.2026` en `de` salen de `Intl.DateTimeFormat().formatToParts()`,
no de una tabla por idioma. Lo único traducible son las letras de la máscara que se ve como
pista, `maskLetters`:

```tsx
<DatePicker locale="en-US" maskLetters={{ day: 'dd', month: 'mm', year: 'yyyy' }} />
```

## Al añadir un componente nuevo

Si el componente emite algún texto que no venga de sus `children` ni de sus datos, ese texto va
en una prop — nunca cableado en el JSX. Es la diferencia entre que un consumidor pueda traducirlo
y que tenga que reimplementar el componente entero para hacerlo.

Lo que cambia con el proveedor es **de dónde sale el valor cuando la prop falta**: en un
componente nuevo, declara su interfaz de textos junto a sus props (como `PaginationMessages`),
añádela a `BrandMessages` y lee con `useBrandMessages('<espacio>')` en el punto donde el texto se
pinta. Sin default castellano.

**Al proveedor va solo lo que el componente emite por su cuenta y dice lo mismo en toda la
suite** —«Acciones», «Ordenado ascendente», el aviso de una tabla vacía—: es cromo del
componente. Lo que es contenido de una pantalla concreta —el `caption` de ESA tabla, el vacío
que explica algo del dominio, el nombre de una fila— **se queda como prop y sin default**: un
catálogo común no puede saberlo, y meterlo ahí es peor error que dejarlo fuera. Mientras un componente siga sin migrar, su prop mantiene el
default castellano y su JSDoc lo dice.

### Las excepciones: `EmailButton.fallbackLabel` y el pie de correo sin cuenta

`fallbackLabel` es obligatoria y **sin default castellano**. Dos razones, y las dos apuntan al
mismo sitio: el correo de la suite vive en seis idiomas que conoce `mailer` y no el DS, y un botón
de correo sin su enlace de respaldo debajo es un correo sin plan B. Hacerla obligatoria es lo que
garantiza que ninguna plantilla se lo deje.

Las otras dos son `optOut.reasonLabel` y `optOut.unsubscribeLabel` del **pie de correo sin
cuenta** (`EmailOptOutGuest`), por la misma lógica: el motivo por el que a alguien sin cuenta le
llega un correo lo sabe el producto que lo manda —no el DS—, y siendo el enlace una frase entera
que cierra ese motivo, ningún default podría encajar. Obligatorias, para que ninguna plantilla
mande una baja sin decir de qué.
