# Tooltip

Bocadillo de ayuda sobre un elemento. Base UI gestiona el retardo, el posicionamiento y el cierre con Escape; el DS pone la superficie (fondo invertido, flecha) y el enlace `aria-describedby` entre disparador y bocadillo. Requiere un `TooltipProvider` por encima, normalmente en el shell, que fija el retardo compartido.

<Canvas of={TooltipStories.Default} />

## Lados

`side` (`top` por defecto, `bottom`, `left`, `right`) y `align` (`start`, `center`, `end`). La flecha apunta siempre al disparador y su base queda pegada al bocadillo, sea cual sea el lado. Esta story es el contrato visual de los cuatro lados.

<Canvas of={TooltipStories.CuatroLados} />

## Separación

La distancia entre disparador y bocadillo sale del token `tooltip.offset` (`spacing.1`, 4px). El Positioner de Base UI necesita un número, así que el componente lee `--tooltip-offset` en runtime sobre `<html>` en cada cálculo de posición: un consumidor la cambia sobrescribiendo el token a nivel de raíz (`:root`). La prop `sideOffset` (px) sigue disponible como override puntual.

## Contenido

`label` admite cualquier `ReactNode`; el ancho máximo (`tooltip.max-width`) parte los textos largos en varias líneas.

## Superficie oscura

En claro el bocadillo ya va invertido: relleno prusia sobre página blanca. Sobre página oscura ese prusia es el propio lienzo, así que toma el par de `Button primary` —relleno lavanda con tinta prusia—, que es lo que manda la regla de derivación para un relleno de marca.

## Como disparador de otro componente

`Tooltip` reenvía `ref` y el resto de props que reciba a **su disparador**, no al bocadillo. Eso es
lo que le permite ser a su vez el disparador de otro componente sobre el mismo botón: un `Popover`,
un `Menu`. Sin ese reenvío, las props que inyecta el motor de fuera (`aria-expanded`, el `onClick`
que abre el panel) se perdían.

```tsx
<Popover trigger={<Tooltip label="Ver los detalles"><Button>Detalles</Button></Tooltip>}>
```

`className`, en cambio, sigue siendo del bocadillo.

## Disparador deshabilitado

Un control apagado es justo el que más necesita explicarse: quien no puede pulsarlo quiere saber por qué. Pero un `button[disabled]` **no sirve de disparador** — el navegador no le manda eventos de puntero y no lo deja recibir foco, así que el bocadillo no se abre ni con el ratón ni con el teclado.

`disabledTrigger` resuelve las dos mitades: el bocadillo se dispara desde un envoltorio focusable (`span.tooltip__trigger`, `tabIndex={0}`) que pone el propio componente, y el CSS apaga los eventos de puntero del hijo deshabilitado para que el hover **sobre el botón** llegue al envoltorio en vez de perderse. Lo segundo es lo que suele faltar cuando esto se monta a mano: el `<span tabIndex={0}>` casero abre el bocadillo con el teclado pero no con el ratón, porque el puntero cae sobre un elemento que no emite nada.

```tsx
<Tooltip label="La matriz está bloqueada: publícala para poder generar los contenidos" disabledTrigger>
  <Button disabled>Generar contenidos</Button>
</Tooltip>
```

<Canvas of={TooltipStories.DisparadorDeshabilitado} />

El control de dentro sigue **deshabilitado de verdad** (`disabled` nativo): no se envía, no se pulsa y el formulario no lo cuenta. Lo que cambia es quién dispara el bocadillo.

La alternativa —que `Button` ganara un `disabledReason` y montara él el bocadillo— se descartó: ataría el átomo más usado del sistema a `Tooltip` y a su proveedor, y lo obligaría a ser componente de cliente en apps que hoy lo pintan desde el servidor. Y el problema no es de `Button`: le pasa igual a un `Select`, a un `Switcher` o a cualquier control apagado.

## Accesibilidad

El bocadillo es `role="tooltip"` y, mientras está abierto, el disparador lo referencia con `aria-describedby` (Base UI no lo cablea por su cuenta). Se abre con hover y con foco de teclado; Escape lo cierra.

### Un control deshabilitado con su motivo

Con `disabledTrigger` el disparador es el envoltorio, así que es él quien recibe el foco y quien lleva el `aria-describedby` al bocadillo: con el teclado se llega al control apagado, se lee su texto y, a continuación, el motivo. Sin el envoltorio no se llegaría siquiera.

Dos cosas que decidir al escribirlo:

- **El motivo va en el bocadillo, no en el nombre del control.** El botón se sigue llamando «Generar contenidos»; lo que se añade es la descripción.
- **Si el motivo tiene que estar siempre a la vista** —una condición que el usuario debe resolver antes de seguir— el bocadillo no es la pieza: es un `Alert` o un texto de ayuda junto al control. Un bocadillo es para la aclaración que se busca, no para la instrucción que hay que leer.

### Cuando el bocadillo solo repite el nombre

Con `describe={false}` el bocadillo **no** se enlaza por `aria-describedby`. Es
para un caso concreto: el bocadillo dice exactamente lo mismo que el nombre
accesible del disparador, porque lo que recorta el texto es el CSS
(`text-overflow: ellipsis`) y la frase entera sigue en el DOM. Describir con el
mismo texto que ya nombra hace que el lector de pantalla lo anuncie dos veces
sin aportar nada: ahí el bocadillo es una ayuda para el ojo, no para el oído.
Lo usa `ConversationList` con el título cortado de una conversación.

Fuera de ese caso, no se toca: un bocadillo que añade algo tiene que estar
enlazado, o no existe para quien no lo ve.
